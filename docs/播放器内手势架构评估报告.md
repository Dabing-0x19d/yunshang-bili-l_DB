## 二、手势状态变量架构

### 2.1 核心状态机

```
触摸事件流：
  Down → [onTD] → 设置 sx_/sy_/st_/sv_/sb_，启动 lt_(500ms) / 检测 dt_(250ms 双击窗口)
    ↓
  Move → [onTM] → 方向判定 → gm_ = 'seek' / 'volume' / 'brightness'
    ↓                 ↑（长按激活后 onTM 直接 return）
  Up   → [onTU] → 收尾：提交 seek / 恢复速率 / 单击-双击判定 / 控制栏显隐
    ↓
  Cancel → [onTC] → 兜底提交 seek / 清理所有定时器
```

### 2.2 状态变量分类

**手势模式控制**（互斥状态机）：
| 变量 | 类型 | 作用域 | 说明 |
|---|---|---|---|
| `gm_` | `string` | Down→Up | 当前手势模式：`''`/`'seek'`/`'volume'`/`'brightness'`，在 onTM 中一次性确定后不再切换 |
| `sk_` | `boolean` | Down→Up | seek 冻结标记，阻止 timeUpdate 回写 ct |
| `sg_` | `boolean` | seek 提交→完成 | seek 在途标记 |
| `ml_` | `boolean` | Down→Up | 是否已移动（区分点击与拖动） |
| `la_` | `boolean` | lt_ 触发→Up | 长按加速激活 |
| `lp_` | `boolean` | lt_ 触发→Up | 长按加速进行中（控制 setRate 恢复） |

**定时器**：
| 变量 | 超时 | 作用 |
|---|---|---|
| `dt_` | 250ms | 双击检测窗口 |
| `lt_` | 500ms | 长按加速触发 |
| `ct_` | 5s | 控制栏自动隐藏 |
| `gt_` | 800ms | 手势提示自动隐藏 |
| `hc_` | 200ms | 延迟隐藏控制栏（已显示→单击→隐藏） |
| `seekBarTouchTimer_` | 1500ms | 进度条触摸窗口看门狗 |

**进度条交互守卫**：
| 变量 | 作用 |
|---|---|
| `sliderDragging_` | 覆盖"按下→提交"阶段，让 PanGesture/onTouch 让位 |
| `seekBarTouch_` | 覆盖"提交→手指抬起"间隙，防 Up 掉进 onTU |
| `seekDragAnchor_` | 进度条按下瞬间的 ct（判断"点了一下没改位置"） |
| `lastSeekBarCommitV_` | 同一目标只提交一次去重 |

**布局切换手势进度**：
| 变量 | 作用 |
|---|---|
| `fsPanProgress` | 右滑全屏进度 0→1 |
| `lsPanProgress` | 左滑切换布局进度 0→1 |
| `swipeProgress` | 详情/评论面板滑动偏移 -1→1 |
| `detailPullDrop` | 下拉关灯进度 0→1 |

## 三、手势优先级与冲突处理

### 3.1 优先级层次

```
Layer 0: 系统手势（下拉状态栏、返回导航）
    ↓ 被 topAreaTouch_ / onBackPress 拦截
Layer 1: 锁定状态（lk=true）→ onTouch 不处理，仅 onClick 解锁
    ↓
Layer 2: 进度条交互（sliderDragging_ / seekBarTouch_）→ onTouch/PanGesture 全部让位
    ↓
Layer 3: PanGesture（右滑全屏 / 左滑切换 / 面板切换）→ 通过 gm_==='seek' 让位
    ↓
Layer 4: onTouch 手势（seek / 音量 / 亮度 / 双击 / 长按 / 单击）
    ↓
Layer 5: 浮动按钮拖拽（关灯/缩小/缓存提示）→ 独立组件，不与 Layer 4 冲突
    ↓
Layer 6: LongPressGesture（点赞三连 / 投币两币 / 文本选取）→ 独立按钮，不冲突
```

### 3.2 核心冲突处理矩阵

| 冲突场景 | 解决方案 | 评估 |
|---|---|---|
| **进度条拖动 vs 播放器手势** | `sliderDragging_` + `seekBarTouch_` 双层守卫 + 1500ms 看门狗 | ⚠️ 脆弱：依赖事件序列假设（Begin→Down→Click→End→Up），看门狗超时后若手指仍在屏上会断链 |
| **seek 手势 vs 右滑全屏** | PanGesture onActionUpdate 检查 `gm_==='seek'` → return | ✅ 有效：onTouch 先于 PanGesture 确定方向 |
| **下拉关灯 vs 水平手势** | onDetailPullTouch 检查 `fsPanProgress > 0.01 \|\| swipeProgress > 0.02` + 横向位移占优检测 | ✅ 有效：双向检测 |
| **双击 vs 单击** | 250ms 定时器窗口 | ⚠️ 代价：单击有 250ms 感知延迟 |
| **长按加速 vs 移动** | onTM 检测移动 > 10vp → 清除 lt_ | ✅ 有效 |
| **顶部状态栏 vs 播放器手势** | `topAreaTouch_` 标记 + 硬编码 `fullscreenTopBarHeight + 16` | ⚠️ 脆弱：常量依赖 AppStorage 值，布局变化时需同步更新 |

### 3.3 PanGesture 优先级修饰不一致

右滑进全屏 PanGesture 在 4 个布局分支中使用了 3 种不同的优先级修饰：

| 布局分支 | 修饰 | distance | 阻尼幂次 | 行号 |
|---|---|---|---|---|
| 常驻层 (buildPlayerOverlay) | `.gesture()` | 20 | 1.2 | 8125 |
| 横屏非全屏 (buildLandscape) | `.gesture()` | 20 | 1.2 | 8575 |
| **竖屏 (buildPortraitLayout)** | **`.priorityGesture()`** | **10** | **1.5** | 8736 |
| 竖屏横看 (buildLandscapeVertical) | `.parallelGesture()` | 20 | 1.2 | 9428 |

**问题**：
1. 竖屏用 `.priorityGesture()` + `distance=10`（更易触发），因为竖屏详情卡片内容会消费普通手势，需要高优先级抢夺。但 `distance=10` 比其他分支的 `distance=20` 更敏感，容易与详情卡片内的 Scroll 滚动产生误触发。
2. 竖屏横看用 `.parallelGesture()`（并行），意味着它与其他手势同时响应，不会互相阻断。这与"右滑进全屏"的独占语义矛盾——并行模式下 seek 手势和右滑全屏可能同时激活。
3. 阻尼幂次不一致（1.2 vs 1.5），竖屏更重是因为详情卡片可滑动距离更短，需要更强的阻尼感来避免误触发。但这个差异没有注释说明。

## 四、架构问题与风险

### 4.1 严重问题

#### P0-1：单击响应有 250ms 感知延迟

**现象**：用户单击视频区域后，控制栏不是立即出现，而是等 250ms 双击窗口超时后才显示。

**根因**：`onTU` 中单击处理逻辑——第一次点击设置 `dt_` 250ms 定时器，超时后才 `cv = true`（显示控制栏）。这是为了区分单击和双击（双击暂停/播放）。

**对比**：`OfflineInlinePlayer` 使用 `GestureGroup(Exclusive, TapGesture(2), TapGesture(1))`，由框架处理互斥，单击延迟由框架内部调度决定（通常更短）。

**影响**：用户感知"点击没反应"，尤其在快速操作时。

**建议**：考虑改用 `GestureGroup(Exclusive)` + `TapGesture`，让框架处理单击/双击互斥。框架的 Exclusive 模式会在双击窗口内延迟单击回调，但延迟通常小于 250ms，且不需要手动管理定时器。需真机验证框架默认延迟。

#### P0-2：双指捏合缩放未实现

**现象**：用户明确需求（记忆 `player-pinch-gesture-scale`）——全屏播放器支持双指捏合切换 AspectFill/AspectFit，但代码中无 `PinchGesture`。

**影响**：功能缺失，用户无法通过手势切换画面填充模式。

**建议**：在 XComponent 上添加 `PinchGesture`，捏合放大 → AspectFill（画面裁切铺满），捏合缩小 → AspectFit（画面完整留黑边）。需注意与 onTouch 的单指手势不冲突（PinchGesture 是多指手势，天然不与单指 onTouch 冲突）。

#### P0-3：seekBarTouch_ 看门狗定时器是脆弱约定

**现象**：进度条交互结束后（onChange End/Click），`seekBarTouch_` 仍保持 true，等待 onTouch Up/Cancel 清除。如果 Up/Cancel 未送达（系统打断、焦点切换），1500ms 看门狗超时后才清除。在此期间播放器手势全部被屏蔽。

**根因**：ArkUI 事件序列假设——onChange 的 End/Click 实测早于 onTouch 的 Up，存在"提交→手指抬起"间隙。但如果系统在 onChange End 之后、onTouch Up 之前打断事件流（如来电、通知弹出），Up 可能永远不到。

**影响**：极端情况下播放器手势被锁死 1500ms。看门狗保证了最终恢复，但期间用户体验受损。

**建议**：看门狗方案已是当前框架限制下的合理妥协。可考虑将超时从 1500ms 缩短到 800ms（手指抬起到 onChange End 的实测间隔通常 < 200ms），减少极端情况下的锁死时间。

### 4.2 中等问题

#### P1-1：右滑进全屏 PanGesture 代码重复 4 份

**现象**：4 个布局分支各有一份 PanGesture(Right) 代码，逻辑几乎相同但有细微差异（distance、阻尼幂次、优先级修饰）。

**影响**：
- 维护成本高：修改阈值/阻尼需同步 4 处
- 行为不一致风险：如 P0-1 所述，竖屏的 distance=10 和其他分支的 distance=20 容易被忽略

**建议**：抽取为 `@Builder` 方法或配置驱动，统一管理差异参数：
```typescript
private buildFSPanGesture(distance: number, power: number, isPortrait: boolean) { ... }
```

#### P1-2：左滑切换布局 PanGesture 代码重复 3 份

同 P1-1，3 个布局分支各有一份 PanGesture(Left) 代码。

#### P1-3：手势状态变量命名极简，可读性差

**现象**：`gm_`、`sk_`、`sg_`、`ml_`、`la_`、`lp_`、`os_`、`dt_`、`lt_`、`ct_`、`gt_`、`hc_`、`sx_`、`sy_`、`st_`、`sv_`、`sb_` 等变量名仅 2-3 字符。

**影响**：新开发者理解成本高，grep 搜索容易误命中（如 `ct` 既是"当前时间"又是"控制栏定时器"）。

**评估**：这种命名在 ArkUI 项目中常见，目的是减少 @State 变量名的字节开销（ArkUI 的状态管理对变量名长度敏感）。但在非 @State 的 private 成员上使用极简命名则没有必要。

**建议**：至少为非 @State 的 private 成员使用描述性命名（如 `gestureMode_`、`seekFrozen_`、`longPressActive_`），@State 变量可保留极简命名。

#### P1-4：阻尼曲线不统一

**现象**：
- 右滑全屏：`Math.pow(offset / threshold, 1.2)` 或 `1.5`（竖屏）
- 左滑切换：`raw * (1.1 - raw * 0.1)`（二次阻力）
- 下拉关灯：`Math.pow(raw, 1.5)`（applyFSResistance）

三种阻尼曲线各自独立，没有统一的阻尼参数管理。

**影响**：不同手势的"拉感"不一致，用户需要适应不同的阻力反馈。

**建议**：定义统一的阻尼曲线配置：
```typescript
interface ResistanceConfig { power: number; threshold: number; }
```

#### P1-5：记忆中的"自动/填充未触发"bug

**现象**（记忆 `player-gesture-fill-auto-bug`）：双指捏合手势的"自动/填充"提示显示但未触发实际行为，同时触发拖动进度与长按倍数锁定。

**根因**：该 bug 已在后续修复中解决，但暴露了手势冲突的深层问题——当多个手势同时激活时，状态变量可能被交叉写入，导致行为不可预测。

**建议**：在 `onTM` 入口添加 `gm_` 互斥断言（debug 模式下），确保同一时刻只有一个手势模式活跃。

### 4.3 低风险问题

#### P2-1：顶部区域保护常量硬编码

`topAreaTouch_` 的判定阈值 `(AppStorage.get<number>('fullscreenTopBarHeight') ?? 96) + 16` 依赖 AppStorage 值和硬编码的 16vp 冗余。如果顶栏高度变化（如不同设备、不同 API 版本），需要同步更新。

#### P2-2：长按加速提示不走 sGH() 函数

长按加速的提示直接设置 `gh/ght/ghtType`，而不是调用 `sGH()`，因为 `sGH()` 会在 800ms 后自动隐藏，而长按加速的提示需要持续到手指抬起。这是合理的特殊处理，但缺乏注释说明原因。

#### P2-3：OfflineInlinePlayer 手势体系与 VideoPlayerPage 独立但结构相似

两个文件都有 `onVT/onTD/onTM/onTU/onTC` 方法，逻辑相似但不完全一致。OfflineInlinePlayer 用 `GestureGroup(Exclusive)` 处理单击/双击，VideoPlayerPage 用定时器。这种不一致增加了维护成本。

**建议**：考虑将核心手势逻辑抽取为共享的 `PlayerGestureHandler` 类，两个页面通过组合方式复用。

## 五、手势交互流程图

### 5.1 触摸事件分发

```
用户触摸视频区域
    ↓
onVT (TouchEvent 总入口)
    ↓
├── sliderDragging_ || seekBarTouch_ → return（进度条交互中）
├── lk (锁定状态) → 不处理，由 onClick 解锁
├── topAreaTouch_ (全屏顶部) → return（让位系统状态栏）
├── Down → onTD
│   ├── dt_ !== -1 → 双击 → togglePP() → return
│   └── 首次点击 → 设置 lt_(500ms 长按计时器)
├── Move → onTM
│   ├── la_ (长按激活) → return
│   ├── adx > 10 || ady > 10 → ml_ = true, 清除 lt_
│   ├── gm_ === '' → 方向判定
│   │   ├── adx >= ady*0.8 → gm_ = 'seek'
│   │   ├── 左半屏 → gm_ = 'brightness'
│   │   └── 右半屏 → gm_ = 'volume'
│   ├── gm_ === 'seek' → 更新 ct + sGH() + 档位震动
│   ├── gm_ === 'volume' → 更新 vol + sGH() + 档位震动
│   └── gm_ === 'brightness' → 更新 bri + sGH() + 档位震动
├── Up → onTU
│   ├── lp_ → 恢复原速率
│   ├── sk_ → 提交 seek
│   ├── 单击 → 250ms 双击窗口 → 显示/隐藏控制栏
│   └── 清理 gm_/ml_
└── Cancel → onTC
    └── 兜底提交 seek + 清理所有定时器
```

### 5.2 PanGesture 与 onTouch 的关系

```
PanGesture(Right) ←→ onTouch(水平 seek)
    ↓
onTouch 先确定 gm_ = 'seek'
    ↓
PanGesture onActionUpdate 检查 gm_ === 'seek' → return（让位）
    ↓
如果 gm_ === ''（未确定为 seek）→ PanGesture 正常响应（右滑全屏）
```

**关键时序**：onTouch 的 Down/Move 先于 PanGesture 的 onActionStart/onActionUpdate（因为 onTouch 是底层事件，PanGesture 是框架识别后的高级事件）。这保证了 seek 手势能先于 PanGesture 确定方向。

## 六、触觉反馈体系

| 场景 | 震动强度 | 触发时机 |
|---|---|---|
| seek 手势开始 | fireHaptic(10) | gm_ 确定为 'seek' |
| seek 档位震动 | fireHaptic(10) | 每跨越 10% 进度 |
| 音量/亮度手势开始 | triggerHaptic() | gm_ 确定为 'volume'/'brightness' |
| 音量/亮度档位震动 | fireHaptic(12) | 每跨越 10% |
| 右滑全屏阈值穿越 | fireHaptic(18) | fsPanProgress 穿越 0.62 |
| 左滑切换阈值穿越 | fireHaptic(18) | lsPanProgress 穿越 0.35 |
| 下拉关灯阈值穿越 | fireHaptic(18) | detailPullDrop 穿越 0.3 |
| 手势取消 | fireHaptic(25) | PanGesture onActionCancel |
| 面板切换触发 | triggerHaptic() | swipeProgress > 0.12 |

**评估**：震动体系设计合理，档位震动（每 10%）提供了离散的位置反馈，阈值穿越震动提供了"即将触发"的预告。但 `triggerHaptic()` 和 `fireHaptic(N)` 两个入口函数的命名差异容易混淆——前者无参数（使用默认强度），后者带强度参数。

| 特性 | 本项目 | OfflineInlinePlayer | 典型视频播放器 |
|---|---|---|---|
| 单击/双击互斥 | 250ms 定时器 | GestureGroup(Exclusive) | GestureGroup 或定时器 |
| 长按加速 | onTouch + setTimeout | onTouch + setTimeout | LongPressGesture 或 onTouch |
| 水平 seek | onTouch (onTM) | onTouch (onTM) | PanGesture 或 onTouch |
| 垂直亮度/音量 | onTouch (左/右半屏) | onTouch (左/右半屏) | 同上 |
| 右滑进全屏 | PanGesture (4份) | 无 | PanGesture 或 SwipeGesture |
| 双指捏合缩放 | **缺失** | 无 | PinchGesture |
| 进度条拖动 | Slider + 双层守卫 | Slider + 简单守卫 | Slider |
| 阻尼曲线 | 3种不统一 | 无 | 通常统一 |
| 触觉反馈 | 完善（档位+阈值） | 简单 | 因应用而异 |

## 九、结论

播放器手势体系整体架构**合理且成熟**，核心设计决策（onTouch 驱动而非 GestureGroup、双层守卫解决进度条冲突、gm_ 互斥状态机）在当前 ArkUI 框架限制下是务实的选择。触觉反馈体系完善，手势提示 UI 与控制栏的双向绑定设计清晰。

主要风险集中在：
1. **功能缺失**：双指捏合缩放是用户明确需求但未实现
2. **感知延迟**：单击 250ms 双击窗口延迟影响操作流畅度
3. **代码重复**：PanGesture 在 4 个布局分支重复，差异参数未统一管理
4. **脆弱约定**：seekBarTouch_ 看门狗依赖事件序列假设

建议优先实现双指捏合缩放（P0），其次评估单击延迟优化方案，再做代码层面的重构（P1）。
