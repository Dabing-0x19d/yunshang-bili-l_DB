## 1. 缩略图预览（P0，主体）

### 1.1 数据链路 —— 已用真实接口跑通

```
GET https://api.bilibili.com/x/player/videoshot?bvid={bvid}&cid={cid}&index=1
headers: User-Agent(PC) / Referer: https://www.bilibili.com/video/{bvid}
```

- **不需要 wbi 签名**：实测 `code=0`；参考项目同样不签名。
- 实测返回（`BV1GJ411x7h7` / `cid=137649199` / 213s）：

  | 字段 | 实测值 | 含义 |
  |---|---|---|
  | `img_x_len` / `img_y_len` | `10` / `10` | 精灵图是 10×10 网格 |
  | `img_x_size` / `img_y_size` | `160` / `90` | **单元格像素尺寸**（不是整图） |
  | `image` | `["//i0.hdslb.com/bfs/videoshot/137649199.jpg"]` | 精灵图列表（长视频多张） |
  | `index` | `[0,0,5,11,17,23,29,34,39,46,...]`（33 项） | **纯秒数**，第 i 格 = 第 i 个秒数的画面 |
  | `pvdata` | `//i0.hdslb.com/bfs/videoshot/137649199.bin` | B 站自己的进度条预览，**用不到** |

- 精灵图实测 **1600×900**（= 10×160 × 10×90）✓ 与 `img_x_size/img_y_size` 完全吻合
- **无防盗链**：不带 Referer 直接 GET 也是 `200`（61KB JPEG）；代码里仍带 UA/Referer 更稳
- **格子命中算法**：目标秒数 `t` → `cell = max(0, count(index[i] <= t) - 1)`
  → `page = cell / 100`（多张精灵图时），`col = cell % 10`，`row = cell / 10`

### 1.2 ArkTS 落地方案

**新增 `api/VideoShotApi.ets`**（照 `api/` 目录既有约定：`http.createHttp()` + `User-Agent` + `Referer` + `getBiliCookie()`）
→ 返回 `VideoShotData { imgXLen, imgYLen, imgXSize, imgYSize, image[], index[] }`

**新增 `services/VideoShotService.ets`**：

- 内存缓存 `Map<cid, VideoShotData>`；**磁盘缓存精灵图**（`filesDir/videoshot/{cid}_{page}.jpg`）
- **按需下载**：只下载当前拖动位置所在的那一张精灵图，不预下全部
- **懒加载时机**：`prepared` + 首帧之后延迟约 1.5s 再拉列表（避开起播竞争）；用户真正开始拖动时才下精灵图
- 失败静默降级（见 §1.6）

**切图（关键，已核对本地 SDK）**：

```ts
const src = image.createImageSource(jpegBuffer);
const pm: image.PixelMap = await src.createPixelMap({
  desiredRegion: { x: col * CW, y: row * CH, size: { width: CW, height: CH } },
  desiredSize: { width: W, height: H },                       // 直接解到显示尺寸
  cropAndScaleStrategy: image.CropAndScaleStrategy.CROP_FIRST
});
```

本地 SDK 已确认存在 `DecodingOptions.desiredRegion` 与 `cropAndScaleStrategy` ✓

- **只解一格**：160×90 RGBA ≈ 57KB；而整张 1600×900 解成 RGBA 是 **5.8MB** —— 这个差别决定内存是否稳
- LRU 缓存 `Map<cellKey, PixelMap>`（上限约 24 格），切 cid 或退出页面时 `release()`

### 1.3 两条通路的接入点（都挂在已有代码上，不新增开关）

| 通路 | 现有落点 | 追加动作 |
|---|---|---|
| 视频区左右滑动 | `onTM` 的 `gm_==='seek'` 分支（已在调 `sGH`） | 再调 `updatePreviewIndex(nt)` |
| 拖动底部进度条 | `onSeekBarInteract_`（已在调 `sGH`） | 再调 `updatePreviewIndex(time)` |
| 松手 | `onTU` / `onSeekBarInteract_(active=false)` | 隐藏缩略图（**保留**现有 800ms 时间提示） |

### 1.4 显示位置：建议按通路区分（方案 A / B）

- **A（推荐先做，两条通路统一）**：沿用现有居中提示胶囊（`position y:'30%'`），在"小进度条 + 时间"**上方**加一张 16:9 缩略图（约 176×99vp）
  - 与 B 站"滑动时画面中央显示卡片"一致；改动最小，不引入新的定位/显隐状态机
- **B（拖进度条时更贴手，后续可选）**：气泡**跟随手指，浮在进度条上方**（B 站原生做法）
  - 需要 `VideoControls` 把进度条几何（轨道左端 x、轨道宽）上报给页面，气泡 x = 目标时间对应位置，并夹在两端内
  - B 是纯加法，做在 A 之上，不推翻 A
- 尺寸参考 PiliPlus：全屏横屏 108 逻辑像素高（16:9 → 192 宽），竖屏 81；再按 `maxHeight - 140` 夹一层上限

### 1.5 与参考实现的差异（有意为之，共 3 处）

| 点 | PiliPlus 做法 | 本计划 | 原因 |
|---|---|---|---|
| 命中格子 | `count(index<=t) - 2` | `count(index<=t) - 1` | `index` 开头有**两个 0**（实测 `[0,0,5,11,...]`），`-1` 才是"最后一个起始时间 ≤ t 的格子"；`-2` 会稳定地退到更早一帧 |
| 行号计算 | `align ~/ imgYLen` | `align ~/ imgXLen` | 参考实现疑似笔误（10×10 网格下看不出来）；本计划按行优先 |
| 查表方式 | `where().length`（O(n)，每次 Move 都算） | 预排序 + 二分（O(log n)） | 拖动时约 90 次/秒，n 可达数百 |

另外参考实现里两个值得抄的兜底：
- `img_x_size == 0` 时按 10×10 整除推导单元格尺寸（有些视频接口不返回尺寸）
- 图片按 URL 做进程内缓存（`previewCache`），并在退出时统一释放

### 1.6 边界与降级（保证"不破坏现有体验"）

| 场景 | 处理 |
|---|---|
| `code != 0` / `index` 为空 | 不显示缩略图，**保留**现有「时间 + 小进度条」提示 |
| 直播（`liveMode`） | 不请求 |
| 本地/离线播放（`OfflineInlinePlayer`） | 不请求（无网、无 cid 映射）；将来若需要可考虑本地抽帧 |
| PGC/番剧 | 先用 bvid+cid 试；失败即降级（后续可补 `avid`/`ep_id` 路径） |
| 分P 切换 | 缓存 key 用 `cid`，天然隔离 |
| 拖到还没下载的精灵图 | 先继续显示上一格（不闪空），后台补下 |
| 弱网 | 精灵图懒加载（真正拖动才下），不预下 |

### 1.7 落地顺序（建议）

1. `VideoShotApi` + 数据模型（拿真实 bvid/cid 校一次格子数与 URL）
2. `VideoShotService`：内存/磁盘缓存 + 单格解码 + LRU
3. 页面状态接线（`previewPm`）+ 手势路径接入 + 居中胶囊渲染（方案 A）
4. 真机验证：逐格切换、0%/50%/末尾三点、降级路径
5. （可选）方案 B：气泡跟随手指
6. （可选）设置项开关（默认开）；补 `AGENTS.md` 与审查报告

## 2. 进度条缓冲进度（P1）

- SDK 已确认：`av.on('bufferingUpdate', (infoType: BufferingInfoType, value: number) => {})`
  - `BufferingInfoType.CACHED_DURATION = 4`，文档原文：**"Estimated duration, in ms, that the buffered data can be played … You can use this event to develop a progress bar."**
  - `BUFFERING_PERCENT = 3` 也有，但 `CACHED_DURATION` 更适合画"能拖到哪"
- 现状：`VideoControls` 的 Slider 只有一层 `selectedColor`（已播放），**看不出缓冲区**
- 方案：在 Slider 下层叠一条缓冲层
  - Slider 自身只能画"轨道 + 已选"两段 → 用 `Stack`：底层一个 `Row`（宽度按百分比）画缓冲段，Slider 的 `trackColor` 设透明、`selectedColor` 保持白色
  - 或者干脆把进度条换成自绘（`Canvas`），为后面的"弹幕热力条/看点标记"一次铺好底子（见 §4/§5）
- 收益：长视频/弱网下能直观看到"能拖到哪"，减少无效 seek 与误以为"卡死"

## 3. 双击左右两侧 ±10s（P1）

- 现状：`onTD` 的双击分支**无条件** `togglePP()`（双击任意位置都是播放/暂停）
- 方案：按触摸 x 分区
  - 左 1/3 → `seek(ct - 10, false, true)`，右 1/3 → `seek(ct + 10, false, true)`，中间 → `togglePP()`
  - 配 `sGH` 提示（`-10s` / `+10s`）+ 一次震动（复用已有档位震动）
  - 竖屏/横屏的分区用容器宽度自适应（已有 `cw` / `lsvw` 可复用）
- 好处：复用第 1 轮就做好的 `fast` 路径（`SEEK_CLOSEST` + 短等待），不会引入新的卡顿
- 注意：必须与现有 `dt_` / `dtp_`（250ms 双击窗口）机制共用，改动集中在 `onTD` 一处

## 6. 其他低成本优化（P2）

- 拖动时**吸附**到最近的看点/章节（§5 的前置）
- 松手后到真正出画之间的 **~0.6–1s 无反馈** → 加一个"缓冲中"小指示
- `Moving` 上报节流：现在约 90 次/秒，每次都写 `@State` + 调 `sGH` → 可合并到每帧一次
- 进度条上标出**"上次看到哪"**（项目已有历史进度存储，只差一个标记）
- 侧边手势区提示增强：左右半屏亮度/音量的图标提示已有，可加"越界"提示
- 遥控器/耳机方向键 seek（`onKeyEvent`），对电视/耳机场景有用

## 7. 不建议做 / 需单独评估

- **`SEEK_CONTINUOUS` 拖动实时预览**：体验上限最高（真正逐帧跟手），但
  1. 本项目是 **DASH 双流**（视频 + 音频两个 AVPlayer），连续 seek 模式**不触发 `seekDone`**，音频这条流的对齐会退化；
  2. `isSeekContinuousSupported()` 在部分设备返回 false，需要回退分支；
  3. 与"拖动期间冻结 `ct` / last-wins / `sg_` 守卫"这套刚稳定下来的机制耦合很深。
  → 建议**单独一轮**做，并大量真机对比，不要和缩略图混在一起改。
- 给 `Slider` 加 `responseRegion`（官方明确不支持，前几轮已纠正）
- 用 `stopPropagation` 替代页面侧守卫（拦不住父节点手势，前几轮已纠正）

## 8. 验证手段（沿用本轮已建立的方法）

- `uitest dumpLayout` 取**物理像素** → 核对缩略图组件的 bounds 与"格子索引 ↔ 目标时间"是否一致
- 截图核对**画面内容与目标时间相符**：至少抽 0% / 50% / 末尾三点（这两轮已多次用这招，能抓出"索引偏一格"这类错）

- 缓冲条：在弱网/长视频下核对 `CACHED_DURATION` 与进度条缓冲段是否同步

### 改动点

- `VideoControls.ets`：新增 `@Link thumb: SeekThumb`，在**已有提示胶囊**里、小进度条上方渲染缩略图；
  `thumb.pm` 为空时不占位 → 无缩略图的视频退回原来的「小进度条 + 时间」，**体验不受影响**
- `VideoPlayerPage.ets`：
  - `case 'prepared':` 后延迟 1.5s 预取列表（避开起播竞争）
  - `onTM` 的手势 seek 分支、`onSeekBarInteract_`（拖动/点击进度条）两处接入 `updateSeekThumb_()`
  - 提示胶囊 800ms 超时隐藏时**一并隐藏缩略图**（复用同一个计时器，不新增第二个状态机）
  - `aboutToDisappear` 释放位图；换 cid（分P/切集）时先松引用再整体释放

### 关键实现点（与计划的差异）

1. **只解一格**：`DecodingOptions.desiredRegion` + `desiredSize` + `cropAndScaleStrategy: CROP_FIRST`
   → 单元格 160×90 ≈ **57KB**；整张精灵图（1600×900）解成 RGBA 是 **5.8MB**。
   （参考实现 PiliPlus 是"整图 Image + srcRect 裁切"，内存占用高一个量级。）
2. **格子命中用二分**：每次 Move 都算，O(log n)；取"**最后一个起始时间 ≤ t**"的格子。
   参考实现用 `count(index<=t) - 2`，实测会退到更早一帧 —— 本次验证点：141s 正确格子是
   `cell=23`，`-2` 会给出 `cell=22`，**两格画面明显不同**（见验证）。
3. **令牌 + 同图去重**：拖动期间 ~90 次/秒的异步查询只允许最后一次写回（否则闪回旧帧）；
   同一张位图已在显示中就不重建对象（省掉一次无用刷新）。
4. **负缓存**：番剧/直播/无缩略图内容只请求一次，之后直接返回 undefined，
   否则拖动期间每秒几十次调用会反复打接口。

## ✅ 实施记录：App 大圆角 + 沉浸光感材质（2026-09-16，真机已验证）

用户要求：圆角采用「App 大圆角」档；材质改用**沉浸光感材质**（即直播页分类胶囊那种）。

### 关键发现：项目已有统一的沉浸材质组件

`components/ImmersiveLightWrapper.ets`（`@ComponentV2`）：

- 直播页分类胶囊就是它：`ImmersiveLightWrapper({ radius: 18, materialStyle: 0, lightIntensity: 2.0 })`
- **本机永远走降级路径**：`aboutToAppear` 里 `materialObj = null; return;`
  （注释写明"systemMaterial 仅在 Navigation 标题栏/底部 TabBar/弹窗内生效"），
  于是实际生效的是 `buildFallback()`：
  `shadow(36, #10000000)` + `backgroundColor(按 materialStyle)` + `border(1.5vp #33FFFFFF)` + `backdropBlur`
- 降级底色按档位：`style≤0 → #12FFFFFF(7% 白)`、`style≤2 → #90000000`、更高 → `#99000000`
- **`fallbackBlurRadius = style ≤ 0 ? 12 : 0`** —— 也就是说只有 style 0 会模糊，style≥1 完全不模糊
- `fallbackColor` 非空时会**覆盖底色**（并同时作为材质 materialColor）→ 这是"既要 style 0 的模糊、
  又要自己控制深浅"的正规出口

### 本次改动（`VideoControls.ets`）

把提示胶囊从"手写样式"换成材质组件：

```ts
Column() {                                   // 只负责定位
  ImmersiveLightWrapper({
    radius: 20,                // App 大圆角
    materialStyle: 0,          // 与直播页胶囊同档
    fallbackColor: '#66000000',// 覆盖 7% 白，压在高亮视频上保证白字可读
    enableLight: false         // 提示胶囊不可点，不需要按压追光
  }) {
    ... 原 seek / volume / brightness 三分支 ...
  }
}
.position({ x: '50%', y: '30%' })
```

- 内容内边距统一 **8**（原 14/12）→ 内容圆角 12，**20 − 8 = 12 完全同心**
- 缩略图圆角 8 → **12**
- 顺手修掉上一轮遗留的不一致：**音量/亮度分支的进度条 6vp → 4vp**（与 seek 分支对齐），
  底色 `0.15 → 0.22` 也统一
- 删掉手写的 `backgroundColor/backdropBlur(20)/border(1vp #1AFFFFFF)/borderRadius(12)`
