# 播放器进度调节审查报告（滑动 seek / 进度条 seek）

审查范围：`entry/src/main/ets/pages/VideoPlayerPage.ets`、`entry/src/main/ets/components/VideoControls.ets`、
参考实现 `entry/src/main/ets/components/OfflineInlinePlayer.ets`
依据：华为官方文档（文末列出，均为 2026-09 最新版）

工程约束：`compileSdkVersion 26.0.0` / `compatibleSdkVersion 6.1.0(23)` → **API 23 起可用**的接口都能用，
下文标注的 API 18/20 级接口（`SeekMode.SEEK_CONTINUOUS`、`isSeekContinuousSupported`、`sliderInteractionMode`、
Slider 的 `enableHapticFeedback`）均在可用范围内。

---

## 0. 现状：两条通路，一个出口

```
视频区手势   onVT → onTD/onTM/onTU                 ┐
                                                  ├→ 共享 ct / sk_ / sg_ → seek(v)（重量级串行流程）
进度条       VideoControls Slider.onChange         ┘
```

- 手势通路：`onVT`(5459) → `onTM`(5537) 改 `ct` 预览 → `onTU`(5627) 调一次 `seek(ct, false)`
- 进度条通路：`VideoControls.ets` 的 Slider(1206) `onChange`，**已经正确处理了 `SliderChangeMode`**：
  `Moving` 只改显示、`Click`/`End` 才 `seekTo(value)`（这一层是对的，比 `VideoPlayerPage.bVC()` 里的旧写法好）
- 出口：`seek(v, rs)`(4705) —— `pause → 双流 seek → await seekDone → play → 等 startRenderFrame(≤3s) → 音频再对齐 → play`

**核心结论：两条通路的手势/UI 层设计基本合理，问题集中在下游那个 `seek()` 的"重"和"不可中断"，
以及两通路之间缺少互斥信号。**

---

## P0 — 功能性缺陷

### P0-1 ★ `seek()` 的 `await seekDone` 没有超时兜底 → 会永久卡死进度调节

`VideoPlayerPage.ets:4719-4728`

```ts
const videoSeekDone = new Promise<void>(resolve => { this.videoSeekResolve_ = resolve; });
this.av.seek(v * 1000);
if (wp) {
  await videoSeekDone;    // ← 无 timeout / 无 finally 兜底
  await audioSeekDone;    // ← 同上
  await this.av!.play();
}
...
} finally { this.sk_ = false; this.sg_ = false; }
```

`sg_` 在 `finally` 里复位。一旦 `seekDone` 因任何原因不回调（`avAudio` 已 release 但引用未清、
seek 目标与当前位置相同、双流 DASH 的 waiting 态），`Promise` 永不 resolve：

- `sg_` 永远为 `true` → **之后所有 seek（手势 + 进度条）都被 `if (!this.av || this.sg_) return` 静默丢弃**
- `sk_` 永远为 `true` → `timeUpdate` 被 `if (!this.sk_)` 挡住 → **进度条冻结，不再随播放前进**

对照组：初始进度路径（`4309-4322`）写了 `Promise.race([Promise.all([...]), timeout])`，交互路径漏了。
修法：`await Promise.race([videoSeekDone, delay(600)])`，并保证 `finally` 一定复位。

### P0-2 ★ `sg_` 是"丢弃"语义，不是"最后一次生效"（last-wins）

`seek()` 开头 `if (!this.av || this.sg_) return`（4706）。seek 在途期间的第二次调节被**彻底丢弃**，
且因为 `this.ct = v` 在守卫之后（4709），连 `ct` 都不更新。用户视角：

- 播放中点进度条 50% → seek 开始（含 ≤3s 首帧等待）→ 用户等不及又点 60% → 第二次请求被丢
- 最终停在 50%，UI 显示 60%，下一次 `timeUpdate` 把进度条**拉回** 50% ⇒ 感知为"点进度条点两次才生效 / 跳回去"

同理，手势拖动松手时若恰有一次 seek 在途，`onTU` 的提交也会被丢掉（`5643`）。

修法：加 `pendingSeekTarget_`，守卫命中时只记目标不执行；在 `finally` 里比对"当前目标 ≠ 已提交目标"则补一次。

### P0-3 ★ 拖动进度条期间没有抑制 `timeUpdate` 对 `ct` 的回写

- `timeUpdate` 处理器：`if (!this.sk_) { this.ct = t / 1000 }`（4431-4433）
- `sk_` 只由手势通路（`onTM` 设 true / `onTU`→`seek()`）和 `seek()` 自己维护
- VideoControls 是独立组件，Slider 拖动时**只改 `currentTime`，不通知页面**，页面 `sk_` 仍为 `false`
- 于是拖动过程中 `timeUpdate`（每秒 1 次左右）把 `ct` 写回真实播放位置，而 Slider 的 `value` 就绑在它上面

表现：**拇指被"拉回"、时间数字跳动**。这也是官方专门给出
[实现 Slider 进度和滑块解耦] 那篇 FAQ 的场景。

修法：VideoControls 增加 `onSeekDragStart` / `onSeekDragEnd` 回调（或一个 `@Link isSeeking`），
`Begin`/`Moving` 置 `sk_ = true`、`End`/`Click` 完成后置回；同时让"拖动预览值"与"播放值"分离：

```ts
@State seekPreviewTime: number = -1;   // -1 表示未拖动
// Slider value: this.seekPreviewTime >= 0 ? this.seekPreviewTime : this.currentTime
```

### P0-4 ★ 手势 seek 灵敏度硬编码，且分母在"横屏非全屏竖屏视频"模式下是错的

`VideoPlayerPage.ets:5578`

```ts
let nt = this.st_ + (dx / this.cw) * this.dur * 0.3;
```

两个问题：

1. **`0.3` 不随时长自适应**。3 分钟视频：整屏宽滑 = 54 秒（够用）；2 小时视频：整屏宽 = 36 分钟，
   即 1vp ≈ 35 秒，**想微调 5 秒物理上做不到**。B 站/爱奇艺的做法是按时长分段给倍率。
2. **`this.cw` 是整屏宽，但该模式下播放器只有 `lsvw` 宽、起点 x=150**（`onTM` 里判定音量/亮度区域时
   已经区分了 `isLandscapeVertical`，见 5559-5565；seek 这条分支忘了区分）→ 同一个手势在不同布局下位移量不同。

建议：

```ts
// 按时长给"一屏宽对应的秒数"
const secPerScreen = this.dur <= 600 ? this.dur * 0.5
                   : this.dur <= 3600 ? this.dur * 0.3
                   : Math.max(this.dur * 0.12, 600);
// 分母用播放器实际可滑动宽度
const trackW = this.isLandscapeVertical ? this.lsvw : this.cw;
let nt = this.st_ + (dx / trackW) * secPerScreen;
```

可再加"位移超过屏宽 60% 后倍率提升"的加速曲线，长视频才拖得动。

### P0-5 `onTC()` 丢弃 seek 且不回滚 `ct` → UI 与真实位置不一致

`VideoPlayerPage.ets:5678-5691`：`onTC` 只做 `this.gm_ = ''; this.sk_ = false`，不提交、不回滚。

官方文档《多层级手势事件》明确列出 Cancel 的触发场景：**按住屏幕按 Home 键、折叠屏折叠切换、
手写笔介入**（实践上还有来电、系统手势截获）。此时进度条停在拖动位置、视频仍在原处，
要等下一次 `timeUpdate` 才被拉回 → 视觉上"进度条莫名其妙跳一下"。

修法：与 `onTU` 一致提交 `seek(this.ct, false)`；或显式 `this.ct = this.st_` 回滚。

## P1 — 体验明显可优化

### P1-1 ★ 未使用官方为"进度条拖动"设计的 `SeekMode.SEEK_CONTINUOUS`

官方 `SeekMode` 枚举（API 18+）原文：

> `SEEK_CONTINUOUS`：该模式提供了一种**画面平滑流畅变化**的 Seek 体验，应用可以结合**进度条控件持续调用 Seek 方法**，
> AVPlayer 根据 Seek 调用持续流畅地更新画面。应用可以调用 `isSeekContinuousSupported()` 判断视频源是否支持。
> 该 Seek 模式不会触发 `on('seekDone')` 事件。退出该模式需调用 `seek(-1, SeekMode.SEEK_CONTINUOUS)`。

`avPlayer.seek()` 的官方示例里直接给了配套写法：

```ts
// SEEK_CONTINUOUS 可以结合 Slider 的 onChange 回调进行对应处理：
// slideMode 为 Moving 时触发拖动过程的 SeekContinuous
avPlayer.seek(slideMovingTime, media.SeekMode.SEEK_CONTINUOUS);
// slideMode 为 End 时结束
avPlayer.seek(-1, media.SeekMode.SEEK_CONTINUOUS);
```

也就是说：**拖动进度条时应该走"连续 seek 预览"，而不是"松手才跳"**。当前实现（Moving 不动、
End 跳一次）虽然避免了冻结，但拖动全程没有画面反馈，离"跟手"差一档。

落地建议：

```ts
// 进入 prepared 后探测一次
this.seekContinuousOk_ = this.av.isSeekContinuousSupported();

// VideoControls onChange
if (mode === SliderChangeMode.Moving && this.seekContinuousOk_) {
  av.seek(Math.round(value * 1000), media.SeekMode.SEEK_CONTINUOUS);
  avAudio?.pause();                    // 双 AVPlayer 架构：拖动中先静音/暂停音频
} else if (mode === SliderChangeMode.End || mode === SliderChangeMode.Click) {
  if (this.seekContinuousOk_) av.seek(-1, media.SeekMode.SEEK_CONTINUOUS);
  this.seek(value, false);             // 提交 + 音频对齐
}
```

不支持时回退到"Moving 只更新 UI、End 提交一次"（即现状）。注意 `SEEK_CONTINUOUS` 不触发 `seekDone`，
所以**不能**把它接到 P0-1 那条 `await seekDone` 的链路上。

### P1-2 ★ `seek()` 为了 seek 而 pause/play，且 seek 后要等最长 3 秒才 play

`VideoPlayerPage.ets:4712-4752`。官方文档：

- `seek()` "只能在 **prepared/playing/paused**/completed 状态调用" → **playing 状态下可以直接 seek，不必先 pause**
- `on('seekDone')`："视频播放：SeekMode 会造成实际跳转位置与用户设置产生偏差，**精准位置需要通过 `currentTime` 获取**，
  事件回调的 time 仅代表完成用户某一次请求"

现状是"先 pause 双流 → 等两个 seekDone → play → **再等 `startRenderFrame`（`Promise.race` 上限 3000ms）** →
读 `currentTime` → 偏差 >50ms 就再 seek 一次音频 → 再等 500ms → 音频 play"。
换来的是音画严格对齐，代价是**点一次进度条要停 0.3~3 秒**。

建议拆成两条路径：

- **点击/松手提交（`seekCommit`）**：`av.seek(t, SEEK_CLOSEST)` → `await Promise.race([seekDone, 600ms])` → `play()`。
  音频偏移交给已有的 `syncAudioVideo` 循环（它能处理 >3s 偏差）兜底，不要在人机交互路径上等首帧。
- **拖动预览（`seekPreview`）**：走 `SEEK_CONTINUOUS`，完全不动音频。

### P1-3 默认 `SEEK_PREV_SYNC` 导致"跳不到点"

`av.seek(v*1000)` 不传 mode → 默认 `SEEK_PREV_SYNC`（跳**上一个关键帧**）。
长 GOP / 低码率片源的关键帧间隔可能十几秒，点进度条会明显"落到前面一点"。
官方给了 `SEEK_CLOSEST`（API 12+）："跳转到距离指定时间点**最近的帧**，建议精准跳转进度的时候用这个枚举值"。
建议：交互 seek 用 `SEEK_CLOSEST`，快进/快退按钮用 `SEEK_NEXT_SYNC` / `SEEK_PREV_SYNC`。

### P1-4 点滑轨可能触发两次 `seekTo`

VideoControls.ets:1233-1240：`Click` 和 `End` 都调 `seekTo(value)`。
官方 `onChange` 说明："**Begin 和 End 状态在点击时触发**，Moving 和 Click 状态在 value 值变化时触发"。
所以**点一下滑轨 = Begin + Click + End**，`seekTo` 被调用两次，目前靠 `sg_` 吞掉第二次 —— 语义脆弱
（`sg_` 一旦按 P0-1 卡死，这里就变成"点一下跳两次"）。

修法：引入一个 `pendingSeek_` 短路标记，或者点击场景只处理 `End`（`End` 在点击时也会触发），
显式去重而不是依赖下游守卫。

### P1-5 进度条触摸热区只有 20vp 高

VideoControls.ets:1221（`.height(20)`）+ 外层 `Row.height(20)`（1252）；`Slider` 未设 `responseRegion`，
而官方文档：`responseRegion` "默认触摸热区为整个组件，默认值 `{x:0,y:0,width:'100%',height:'100%'}`"。

也就是说**实际可点区域只有 20vp 高**。官方那条"从 API 26 起 Button/Toggle/Select/Chip 默认最小热区
28→32vp"的变更**不覆盖 Slider**，得自己加：

```ts
.responseRegion({ x: 0, y: -12, width: '100%', height: 44 })
```

否则"想点进度条却点到视频区"，被 `onVT` 判成单击 → 反而把控制栏隐藏了，是当前"点进度条不准"的高频原因之一。

### P1-6 `blockColor(Color.Transparent)` → 滑块不可见

VideoControls.ets:1219。加上非全屏时 `trackColor` 默认透明（1217），静止状态下进度条只剩一条
越来越长的白线，**没有"可抓取点"的视觉锚**，用户不知道自己该抓哪儿（官方 FAQ
《使用Slider时如何判断点击的是滑块还是进度条》讨论的前提就是滑块是可见的）。
建议给个 8~10vp 的白色/主题色滑块，或至少拖动（`seekTrackVisible`）时淡入。

### P1-7 拖动中 `ip` 未置位 → 15 秒自动隐藏仍可能生效

`schedAH()`（3921-3926）：`if (this.cv && !this.lk && !this.ip) setTimeout(hide, 15000)`。
`ip` 只被比例/画质/更多等弹窗置位，**Slider 拖动全程不置位**，`Moving` 阶段又不调 `seek()`
（`seek()` 末尾的 `cancelDelayHide()` 只清 `hc_`，本来也不重置 15s 计时器）。
长视频上连续拖动超过 15 秒，控制栏会在手指底下消失。
修法：`Begin` 置 `ip = true`，`End`/`Click` 后置回并 `resetCT()`。

### P1-8 手势 seek 没有档位震动反馈

音量/亮度都有"每跨越 10% 档位震动一次"（5605-5608 / 5620-5623），手势 seek 只在
手势开始时 `triggerHaptic()` 震一次，拖动全程无反馈，三种手势手感不对称。
建议按"每跨越 5%/10% 进度"或"每跨过整分钟"触发 `fireHaptic(10)`。

## P2 — 健壮性 / 一致性

| # | 问题 | 位置 | 说明 |
|---|------|------|------|
| P2-1 | 手势方向锁阈值过低 + 判定放宽 | 5544-5553 | `adx > 10 \|\| ady > 10` 才起判，且 `adx >= ady * 0.8` 视为横向（0.8 意味着垂直位移是水平的 1.25 倍仍判横向）。手指初始抖动即可决定整段手势，且 `gm_` 锁定后不可纠正 → 斜滑误判率偏高。建议阈值抬到 12~16vp，或累积 2~3 帧再定向 |
| P2-2 | 自研 onTouch + 框架 PanGesture 跨机制协调 | 7417 的 `onTouch` vs 7420 的 `PanGesture(Right)`，靠 `gm_ === 'seek'` 互相避让 | 官方《多层级手势事件》明确："绑定手势方法属性可以控制手势的竞争，**但不能影响到 onTouch 事件**"。用普通变量在两个机制之间做约定，依赖回调时序（规范未保证）→ 建议把"右滑进全屏"和"滑动 seek"放进同一个 `GestureGroup(GestureMode.Exclusive)`，或用 `onGestureRecognizerJudgeBegin` 统一裁决 |
| P2-3 | 时长未知时手势 seek 无效但仍弹提示+震动 | 5578-5582 | `dur <= 0`（加载中/直播）时 `nt` 恒等于 `st_`，却照常 `sGH(...)` 且已 `triggerHaptic()`。应 `if (this.dur <= 0) return` |
| P2-4 | Slider 量纲与时长耦合 | VideoControls 1206-1211 | `max: duration > 0 ? duration : 100`，`value: currentTime`（秒）。`duration = 0` 时 `max` 变成 100，与 `currentTime` 不同量纲；`step: 1`（秒）在窄轨道上无意义（2h 视频轨道约 205vp → 1px ≈ 35 秒）→ 长视频需要"拖动加速"或长按细调 |
| P2-5 | 多点触控未处理 | `onTD/onTM` 只用 `e.touches[0]`，不按 `t.id` 跟踪 | 官方《手势事件冲突常见问题》给了 `monopolizeEvents(true)` 解决多点触控下多组件同时响应；至少应在 `e.touches.length !== 1` 时忽略 |
| P2-6 | `sliderInteractionMode` 未设置 | VideoControls 1206 | 默认 `SLIDE_AND_CLICK`（**按下滑轨立即跳到该处**）。视频播放器通常期望 `SLIDE_AND_CLICK_UP`（抬手才生效），配合 `SliderChangeMode` 可让"点=单次跳转、拖=连续预览"语义清晰 |
| P2-7 | 触感可能重复 | Slider 默认 `enableHapticFeedback(true)`（API 18+，需 `ohos.permission.VIBRATE`，工程已声明） | Slider 自带触感 + 应用 `fireHaptic()` 可能叠震。要么统一走 Slider，要么显式 `enableHapticFeedback(false)` |
| P2-8 | `minResponsiveDistance` 未设 | VideoControls 1206 | API 12+，默认 0。默认值对本场景是对的，但显式写 0 可避免后续被主题值改动影响 |
| P2-9 | 无障碍缺失 | 进度条 / 手势提示 | 未设 `accessibilityText` / `accessibilityDescription`，读屏用户无法调节进度 |
| P2-10 | 拖动中 `currentTime` 每帧写 `@State/@Link` | VideoControls 1225 | 60fps 下每秒 60 次跨组件状态写；建议拖动中用局部 `@State` 承载预览值，`End` 时才回写 |
| P2-11 | 死代码 | `VideoPlayerPage.bVC()` 5693-5817 | 全段**无任何调用点**（`grep bVC` 只有定义），里面还留着旧的 `Slider.onChange((v) => this.seek(v/100, ...))` 写法。极易误导后续排查与改错文件，建议删除 |
| P2-12 | 同类问题已被复制到离线内嵌播放器 | `OfflineInlinePlayer.ets:947 / 1113` `.onChange((v) => { this.seekTo(v); })` | 每次 `onChange`（含 `Moving`）都调 `seekTo`，而 `seekTo` 会等**两个** `seekDone`（最长 2 秒）→ 拖动时大量并发被丢，比主播放器更严重。修主播放器时应同步 |

## 建议的落地顺序

1. **P0-1 / P0-2**：给 `seek()` 加超时兜底 + last-wins `pendingSeekTarget_`。
   改完 `seek()` 从"可能永久锁死"变成"最坏慢一次"，风险最低、收益最大。
2. **P0-3**：加 `onSeekDragStart/End` 回调（VideoControls ↔ 页面互斥信号），解决拇指回跳。
3. **P0-4 / P0-5**：灵敏度按时长+按模式宽度自适应；`onTC` 提交或回滚。
4. **P1-1**：接入 `SEEK_CONTINUOUS`（含 `isSeekContinuousSupported()` 回退）。
5. **P1-3 / P1-2**：交互 seek 用 `SEEK_CLOSEST`；把"等首帧 ≤3s"从交互路径移除。
6. **P1-4 ~ P1-8**：去重、热区、滑块可见性、`ip` 互斥、档位震动。
7. 清理 P2-11 死代码，同步修 P2-12。

## 追加：真机验证后的补充（两条新发现 + 一组实测数据）

### A. 点击滑轨的完整事件序列（hilog 实测，修正了原先的推断）

```
onChange(Begin, value 已是跳转后的新值)
  → onTouch(Down)
    → onChange(Click, 同值)
      → onChange(End, 同值)
        → onTouch(Up)
```

两个原先没料到的点，都直接决定实现正确性：

1. **Begin 早于 `onTouch Down`，且 Begin 的 value 已经是跳转后的新值。**
   原报告 P0-3 建议「加 `SliderChangeMode` 驱动的互斥」，本轮实现时曾退化成
   「`onTouch` Down 记锚点 + Up 提交」，结果 **点击滑轨完全失效** ——
   因为 Down 读到的 `currentTime` 早已是目标值，锚点==目标，位移判定为 0，提交被吞。
   **正确锚点必须取页面自己的播放位置**，且交互上报要在 `currentTime = value` **之前**。
2. **`Click` 与 `End` 连续触发且值相同**，必须按同值去重，否则一次点击提交两次 seek。

结论：**提交点应放在 `onChange` 的 `End`/`Click`**，`onTouch` 只保留「`Cancel` 兜底解冻」。

### B. 新发现：进度条上「向左拖」会切换面板（已修）

`VideoPlayerPage.ets` 卡片层的面板切换手势：

```ts
PanGesture({ direction: this.at === 0 ? PanDirection.Left : PanDirection.Right, distance: 10 })
```

`distance` 仅 10，是全局最容易抢到触摸的一条；它**没有** `sliderDragging_` 守卫（另外 4 处有）。
在进度条上向左拖动会被它抢走 → 切到评论/推荐面板（`at` 0→1），进度条随之消失。
**向右拖不会触发**（`at === 0` 时它只认 `Left`），所以这个缺陷很容易漏测。

修法：在其 **`onActionStart` 首行**加 `if (this.sliderDragging_) return;`。
只拦 `onActionUpdate` 不够 —— `Start` 已经把 `isSwiping` 置为 true 了。

### C. 另一处修正：触摸热区不能用 `responseRegion`

本轮一度按报告 P1-5 写 `.responseRegion({ y: -12, height: 44 })`，
后经官方 `slider.d.ts` 核实：**Slider 明确不支持 `responseRegion`**
（"All the universal attributes except responseRegion are supported"），该属性对 Slider 无效。

改法：把 **Slider 自身布局盒**撑高 —— `.height(20)` → `.height(44)`，
并把外层进度行同样改为 44（否则 Slider 溢出父行、在非全屏下压到下方按钮行顶部抢点击）。
OutSet 样式下轨道/滑块在盒内垂直居中，抬高 height **不改变轨道视觉位置**。

真机布局 dump 验证：`Slider [188,1076][1915,1188]` → 高 112px ÷ 密度 2.545 ≈ **44vp** ✓

## 追加 2：修复「点击/拖动后时间不跳、控制栏收缩一下」（上一轮改动引入的回归）

### 根因

上一轮把提交点从 `onTouch` 的 Up 改到 `onChange` 的 End/Click 是正确的，但同时做了两件有害的事：
**移除了 Slider 的 `stopPropagation`**，并且**在提交的那一刻就释放了 `sliderDragging_`**。
而实测事件顺序是 `Begin → Down → Click → End → Up` —— **Up 在提交之后**。于是手指抬起时：

1. `onVT` 的 `sliderDragging_` 守卫已经失效 → 触摸落到播放器手势状态机 → **`onTU` 被调用**；
2. `onTU` 里这一行是致命的：

   ```ts
   if (this.sk_ && this.av) { this.sk_ = false; this.seek(this.ct, false, true); }
   ```

   此刻刚提交的 seek **仍在途**（`sk_` 为 true），这一行把 `sk_` 强行清零 →
   `timeUpdate` 立刻把 `ct` 写回**旧播放位置** → Slider 的 value 与时间文本一起回退。
   **用户看到的就是「点了/拖了进度条，时间没有跳到目标」。**
3. `onTD` 因为守卫从头到尾没执行过 → `ml_`/`wcv_`/`dtp_` 全是上一次手势留下的陈旧值 →
   `onTU` 走进"单击视频区"分支 → `hc_` 200ms 后隐藏控制栏、`dt_` 250ms 后再尝试显示
   （且 `dtwcv_` 陈旧为 true 时直接保持隐藏）→ **用户看到的就是「控制栏收缩一下」。**

另外，重写 `onChange` 时把原实现的 `Click` 分支 `animateTo(180ms)`（点击处平滑滑到位）一起删掉了。

### 修法

1. **新增 `seekBarTouch_` 触摸窗口标记**：从交互上报开始保持到手指真正抬起 ——
   `onVT` 收到 `Up`/`Cancel` 才撤销，另加 1500ms 看门狗防止 Up 丢失导致守卫永久生效。
   `onVT` 的守卫改为 `if (this.sliderDragging_ || this.seekBarTouch_)`。
   为什么不直接用回 `stopPropagation`：实测它并不影响 Slider 自身的 click-jump（上一轮那个失效
   其实是**锚点**的问题），但用页面侧显式标记比依赖跨组件事件拦截语义更可控 ——
   而且官方明确它拦不住父节点手势，几处 `PanGesture` 本来就得自己 `return`。
2. **`sk_` 只在"本次没有提交 seek"时才自己解冻**：三处收尾分支统一改为 `if (!this.sg_) this.sk_ = false;`。
   提交了 seek 就交给 `seek()` 的 `finally` 复位，避免在途期间被 `timeUpdate` 抢写。
3. 恢复 `Click` 分支的 `animateTo(180ms)` 平滑滑到位。

### 真机验证（lv 竖屏横看布局；dur=13:05=785s；控件盒 [208,575][1235,687]）

轨道两侧各有约 2.4%（≈10vp）内缩，按 `value = 785 × (f − 0.024) / (1 − 2×0.024)` 换算：

| 操作 | 预期 | 实测（+0.8s） | 判定 |
|---|---|---|---|
| 点击滑轨 25% | 186.0 | **185.97** | ✓ |
| 点击滑轨 75% | 599.0 | **599.00** | ✓ |
| 向左拖到 15% | 104.0 | **104.85** | ✓ |

三次操作 +2.0s 的读数都是「目标 + 约 4 秒播放」→ 时间显示**从新位置继续推进、不再回退**；
每次探测都能查到 Slider（bounds 不变）→ **控制栏没有被隐藏**。

日志侧（临时插桩，验证后已移除）确认：`onTU RAN` = **0 次**、`hc_ FIRED` = **0 次**、
每次交互 `COMMIT` **恰好 1 次**（Click 与 End 同值走 dedupe）；
其中第一次点击恰好点在当前位置附近，正确命中 `no-move → 跳过提交`（没做无意义的 seek）。

### 教训（可复用）

**"提交点"和"释放守卫的时机"是两个独立的东西。** 提交可以发生在 `End`/`Click`，
但一次触摸的"生命周期结束"在 `onTouch` 的 `Up` —— 两者不是同一个时刻。
任何"触摸期间让位"的守卫都必须覆盖到**真正抬起**，否则 Up 会以陈旧的手势状态掉进
播放器自己的单击/滑动逻辑，产生一串看起来毫无关联的副作用（时间回退、控制栏闪、重复 seek）。

## 追加 3：拖动/点击底部进度条也显示「时间 + 小进度条」提示

原先 `sGH()`（提示胶囊）**只在手势路径 `onTM` 被调用**，所以只有视频区左右滑动才有提示；
拖动底部进度条时看不到目标时间 —— 而拇指恰好压住进度条本身，最需要这个提示。

### 改法（复用现成 UI，不新增任何组件）

- `VideoPlayerPage.onSeekBarInteract_`：在 `seekBarTouch_` 续期之后、分支之前插入

  ```ts
  if (this.dur > 0) {
    this.sGH(this.formatDuration(Math.round(time)), time / this.dur, 'seek');
  }
  ```

  - 拖动期间每条 `Moving` 上报都会续期 —— 与手势路径同频（`sGH` 本来就是按 Move 频率调用的），
    整段拖动常驻、松手后 800ms 自然淡出；
  - 点击滑轨时 `End`/`Click` 那次上报让它闪一下，确认「已跳到目标」；
  - `dur <= 0` 不弹，与手势路径的守卫一致（时长未知时比例无意义）。
- `OfflineInlinePlayer.onSeekBarChange_`：同样加
  `if (this.duration > 0) this.showGestureHint(this.formatTime(Math.round(v)), v / this.duration);`
  （该组件有自己的提示状态机 `ghShow/ghText/ghProgress` 与 UI，保持两处体验一致）。
